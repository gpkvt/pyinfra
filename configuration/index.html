    Host configuration

    DEFINE THE DESIRED STATE

    Configure each machine with tracked examples and private local data. Keep feature choices readable, credentials protected and task logic reusable.

    group_data/Host and role settings
    workstationOpt-in desktop features
    secretsEncrypted credentials

    Host-specific desired state is stored as Python data in group_data/. pyinfra exposes the values for a target through host.data. Real machine configuration is intentionally untracked: .gitignore excludes group_data/@local.py and group_data/workstation.py. The repository tracks portable templates at group_data/@local.py.example and group_data/workstation.py.example instead.

    After cloning, create local copies before deploying:

    cp group_data/@local.py.example group_data/@local.py
cp group_data/workstation.py.example group_data/workstation.py

    Edit both files for the target machine. Replace every identity placeholder, verify hardware and network settings, and explicitly enable only the workstation features required on that host. Keep credentials, private keys, USB device rules, real hostnames, IP addresses and other machine-specific data in the ignored local files. Do not force-add these files to Git.

    Which files are used?

    The inventory target name determines its host-data file: the local target uses the ignored group_data/@local.py, and a target named web01 uses group_data/web01.py. Inventory groups can add shared configuration for a role or class of hosts. For example, workstation = ["@local"] in inventory.py makes @local a member of the workstation group, so pyinfra also loads the ignored group_data/workstation.py. Group data and host data are both available through host.data; keep role-wide defaults in the workstation file and host-specific overrides in the local file.

    The workstation group is optional. Add a host to the workstation inventory group only if it should receive that role's configuration and eligible workstation tasks.

    Keep configuration data separate from task logic. Put private keys, passwords, API tokens and credential-bearing URLs in the encrypted secrets file, not in group data. Use the deployed gpg-vault command to manage that file without routinely handling plaintext manually. See Secrets management.

    Common settings

    Setting Purpose Notes
    hostname System hostname Managed by tasks/system.py.
    username Primary user Used by user-scoped tasks; some tasks default to root if omitted.
    usergroup Primary group Used by user-scoped tasks; some tasks default to root.
    homedir User home directory Also published as builtins.homedir; defaults to /root/ in common.initialize().
    timezone System timezone Use a valid zoneinfo identifier.
    locale System locale Defaults to en_US.UTF-8 in the system task; set to None to skip locale management.
    keyboard XKB keyboard configuration Empty dictionary disables management.
    editor / visual_editor Default editors visual_editor falls back to editor.

    Example:

    hostname = "workstation"
username = "deploy"
usergroup = "deploy"
homedir = "/home/deploy"
timezone = "Etc/UTC"
locale = "en_US.UTF-8"
editor = "vim"

    Workstation role

    The tracked group_data/workstation.py.example defines a shared, nested workstation configuration. Copy it to the ignored group_data/workstation.py and edit it locally. deploy.py checks each feature's enabled flag and includes its corresponding task only when that flag is true. The example disables every feature until explicitly enabled.

    Setting Default in tracked example Effect
    workstation.backup.enabled False Installs Restic, Borg, rsync and Borgmatic, and renders /etc/borgmatic/config.yaml. It does not create or run a backup job; repository locations, credentials, sources, retention and restore testing still need configuration.
    workstation.power.enabled False Installs and enables the selected power manager. manager must be tlp or power-profiles-daemon; the other manager is removed.
    workstation.hardware.enabled False Installs fwupd and, when selected, CPU microcode (intel or amd). Firmware updates are not applied automatically.
    workstation.storage.enabled False Installs smartmontools and nvme-cli; no monitoring schedule or alerting is configured.
    workstation.peripherals.enabled False Enables optional printer/scanner support. Set printing and/or scanning to true; CUPS is enabled when printing is selected.
    workstation.desktop.enabled False Installs common desktop integration utilities. packages can replace the default package list.
    workstation.maintenance.enabled False Installs needrestart, debian-goodies and apt-file; no unattended upgrades or automatic reboots are enabled.

    Example role configuration:

    workstation = {
    "backup": {"enabled": True},
    "power": {"enabled": True, "manager": "tlp"},
    "hardware": {"enabled": True, "cpu_vendor": "amd"},
    "storage": {"enabled": True},
    "peripherals": {
        "enabled": False,
        "printing": False,
        "scanning": False,
    },
    "desktop": {"enabled": False},
    "maintenance": {"enabled": False},
}

    COSMIC configuration is nested exclusively under workstation.cosmic; do not define a separate top-level cosmic variable in per-host data. The COSMIC deployment includes independently gated appearance, window management, input, shortcuts, panel, dock and workspace modules. Display/output settings are intentionally excluded.

    Optional custom COSMIC configuration directories can be synchronized with workstation.cosmic.config_files. Each entry is a mapping with a repository-relative src directory and a destination dest relative to the configured user's home directory:

    workstation = {
    "cosmic": {
        "enabled": True,
        "config_files": {
            "appearance": {
                "src": "files/cosmic/local/appearance/",
                "dest": ".config/cosmic/com.system76.CosmicTheme.Mode/v1/",
            },
            "panel": {
                "src": "files/cosmic/local/panel/",
                "dest": ".config/cosmic/com.system76.CosmicPanel.Panel/v1/",
            },
            "dock": {
                "src": "files/cosmic/local/dock/",
                "dest": ".config/cosmic/com.system76.CosmicPanel.Dock/v1/",
            },
        },
    },
}

    The source directories are synchronized as supplied, with files owned by the configured user and group. Keep machine-specific files and secrets out of tracked source directories. Do not put display/output configuration in these directories if the goal is to keep display layouts machine-specific.

    The tracked workstation example disables all features by default. Review each feature's requirements before enabling it. In particular, the backup task only installs tools and deploys a Borgmatic configuration template; it does not configure repository credentials or schedule backups. The current Borgmatic template also contains a literal fallback encryption passphrase (B0rgm4t1C!) and the generated file is mode 0600; do not use that fallback for real backups. See Templates and static assets for the security caveat.

    Network and name resolution

    hostnames maps IP addresses to one or more hostnames and is consumed by tasks/hosts.py to manage /etc/hosts.

    hostnames = {
    "127.0.0.1": ["localhost"],
    "::1": ["localhost"],
    "192.0.2.10": ["app.example.test", "app"],
}

    Each IP address must map to a list; space-separated strings are no longer accepted. Convert an old value such as "app.example.test app" to ["app.example.test", "app"]. An empty list removes all entries for that IP address from /etc/hosts.

    VPN-related settings:

    Setting Purpose
    local_network_cidr IPv4 CIDR used to detect whether the host is on the trusted/local network.
    wireguard_interface Interface name used by the VPN service task.
    wireguard_config Mapping of interface names to WireGuard interface settings.

    The VPN task currently checks globally scoped IPv4 addresses only. It starts/enables wg-quick@<wireguard_interface> when none belongs to the configured local CIDR. It does not evaluate IPv6 network membership.

    Packages and repositories

    • apt_packages: list of Debian package names installed by tasks/apt.py.
    • apt_sources: mapping of repository identifiers to signing-key and APT source definitions. The task uses apt.key to install/dearmor signing keys and creates .list source files. Keyring paths must end in .gpg and must match each repository's signed-by option.
    • flatpak_packages: list of Flatpak application IDs. tasks/flatpak.py is included only when the Flatpak executable is detected. Flatpak installations and updates retry failures three times with five seconds between retries, then allow the remaining deployment tasks to continue if the remote remains unavailable. Errors remain visible; unsuccessful packages are not considered installed and must be retried later.

    Example:

    apt_packages = ["curl", "git", "rsync"]
flatpak_packages = ["org.mozilla.firefox"]

    Review third-party repository URLs, distributions, architectures and signing-key sources before enabling them.

    Example:

    zshrc_imports entries are rendered into the generated .zshrc; ensure referenced files exist for the configured user. Keep credentials out of these files unless they are protected separately.

    On-demand Samba file exchange

    The optional top-level samba mapping enables a guest-accessible LAN/VPN file exchange server. It provides a shared writable Upload dropbox and a read-only Download share. The task installs and configures Samba but leaves smbd stopped and masked; use the deployed samba-start and samba-stop commands to open/close TCP 445 in UFW and start/stop the service. Configure trusted CIDRs explicitly. Upload guests share one Unix identity and can manage one another's files; this is a convenience dropbox, not private per-device storage. See Samba documentation for the full configuration and security model.

    Example:

    samba = {
    "enabled": True,
    "interface": "enp3s0",
    "allowed_networks": ["192.168.1.0/24"],
    "idle_timeout": 3600,  # 0 disables automatic shutdown
    "upload": {"path": "/srv/samba/upload"},
    "download": {"path": "/srv/samba/download"},
}

    Service configuration

    Docker

    docker is a mapping of service names to service-specific settings. The supported keys are adguard_home, appflowy, miniflux, timetagger, grav, forgejo, portainer, tasmoadmin, wallabag, vaultwarden, nocodb, linkwarden, homepage, paperless, firefly-iii, snipe-it, mdmesh and wg-easy. Each service has its own options; inspect its module under tasks/docker/ and its Compose template under templates/docker/<service>/ before adding keys.

    All current services persist application data through host bind mounts below the configured user's home directory:

    Service Persistent host path Default loopback port
    Miniflux ~/.docker/miniflux/db/ (PostgreSQL database) 8080
    TimeTagger ~/.docker/timetagger/ 8080
    Grav ~/.docker/grav/data/ 8080
    Forgejo ~/.docker/forgejo/data/ 8027 (HTTP), 2222 (SSH)
    Portainer ~/.docker/portainer/data/ 9000
    TasmoAdmin ~/.docker/tasmoadmin/data/ 8016
    Wallabag ~/.docker/wallabag/data/, ~/.docker/wallabag/images/ 8017
    Vaultwarden ~/.docker/vaultwarden/ 8018
    NocoDB ~/.docker/nocodb/data/ 8019
    Homepage ~/.docker/homepage/config/ 8020
    Paperless-ngx ~/.docker/paperless/postgres/, data/, media/, consume/, export/ 8022
    Linkwarden ~/.docker/linkwarden/postgres/, data/, meili/ 8021
    Firefly III ~/.docker/firefly-iii/database/, upload/, fints/ 8023 (FinTS importer: 8024)
    Snipe-IT ~/.docker/snipe-it/database/, storage/ 8025
    AppFlowy ~/.docker/appflowy/postgres/, minio/, search/ 8026
    WG-Easy ~/.docker/wg-easy/ UI 51821; WireGuard UDP 51820

    The interfaces bind to 127.0.0.1 by default, except explicitly published protocol ports such as WG-Easy WireGuard UDP. All persistent service data uses direct host bind mounts below ~/.docker/, not Docker-managed named volumes. The shared Docker helper renders Compose files under ~/.docker/<service>/ and user-level systemd units under ~/.config/systemd/user/. A changed Compose file triggers an image pull and container preparation; unchanged Compose files do not trigger a pull. User-level systemd units manage the Compose projects, while Sablier can start labelled services on demand when enabled.

    Service-specific behavior:

    • AppFlowy deploys the official AppFlowy Self-Hosted Commercial Compose stack behind the existing Caddy instance. The public hostname is appflowy.21x9.org; Nginx publishes only 127.0.0.1:8026. PostgreSQL, MinIO and Search persist in ~/.docker/appflowy/postgres/, minio/ and search/ using host bind mounts. The task creates ~/.docker/appflowy/.env with mode 0600 from encrypted secrets. Configure secrets.docker.appflowy.postgres_password, admin_password, jwt_secret, minio_access_key and minio_secret_key. The initial administrator password must be at least 16 URL-safe characters. Generate the PostgreSQL password, JWT secret and MinIO secret key with openssl rand -hex 32; generate the exactly 20-character MinIO access key with openssl rand -hex 10. The first GoTrue administrator is created from docker.appflowy.admin_email (default admin@appflowy.21x9.org) and the encrypted admin_password. Change the initial password after first login. Cloud, AI, Worker and Search receive their respective Redis connection URLs from the generated environment file and connect to the Compose redis service, never container-local localhost. Redis follows the upstream ephemeral configuration and has no persistent data mount or AOF; pending queue state may not survive Redis replacement. SMTP and AI provider keys are optional and remain unset by default. AppFlowy is the commercial self-hosted distribution; review the upstream license before deployment. Homepage only links to AppFlowy and does not call its authenticated API.

    • Miniflux runs with a PostgreSQL companion container. Set docker.miniflux.postgres_version explicitly and optionally configure port; credentials are supplied through secrets.docker.miniflux. Deployment fails if the PostgreSQL version is missing or invalid.

    • TimeTagger mounts its persistent directory at the container's /root/_timetagger.
    • Grav supports image, port, channel, setup, scheduler and fix_permissions options.
    • Forgejo supports image, port, ssh_port, ssh_server and domain. HTTP and SSH bind to loopback by default. The configurable HTTP host port defaults to 8027 and maps to container port 3000. If an existing host sets docker.forgejo.port explicitly, update it and the corresponding Caddy reverse_proxy target together.
    • Portainer mounts the Docker socket, giving it administrative control over the Docker host. Keep its interface private or protect the reverse-proxy route with strong authentication.
    • TasmoAdmin mounts its data at /data/tasmoadmin inside the container, matching TASMO_DATADIR.
    • Wallabag uses SQLite, stores its database/application data and article images in the two host directories above, and disables public registration. Change the initial wallabag / wallabag account password immediately. The supplied local configuration publishes it through Caddy at wallabag.21x9.org.
    • Vaultwarden disables public signups and invitations. Its optional admin_token secret must contain an Argon2 PHC hash, generated with docker run --rm -it vaultwarden/server:latest /vaultwarden hash. The supplied local configuration publishes it through Caddy at vaultwarden.21x9.org.
    • NocoDB persists its application data in ~/.docker/nocodb/data/, mounted at /usr/app/data. It supports image, port and domain; the supplied local configuration publishes it through Caddy at nocodb.21x9.org.
    • Homepage persists its configuration in ~/.docker/homepage/config/, mounted at /app/config. It supports image, port and domain; domain is passed to HOMEPAGE_ALLOWED_HOSTS and must contain the hostname (and port, if applicable), not a URL scheme. The supplied local configuration publishes it through Caddy at homepage.21x9.org. Docker socket integration is not enabled by default. Since widgets can display sensitive data, protect the dashboard with reverse-proxy authentication, Homepage authentication, or a VPN.
    • Paperless-ngx runs PostgreSQL 17, Valkey, Gotenberg and Tika alongside the web application. PostgreSQL and Paperless application directories are mounted directly from ~/.docker/paperless/ on the host. Set uid and gid to the numeric user/group IDs that should own Paperless data (defaults to 1000:1000); PostgreSQL storage is owned by UID/GID 70:70. Configure postgres_password (URL-safe) and secret_key in secrets.docker.paperless. The web interface binds to loopback port 8022 and the supplied local Caddy hostname is paperless.21x9.org.
    • WG-Easy stores WireGuard configuration in the host bind-mounted directory ~/.docker/wg-easy/. Its web UI binds to 127.0.0.1:51821 by default and is published through Caddy at vpn.21x9.org; WireGuard listens on public UDP port 51820. The first visit opens the WG-Easy setup wizard: configure the public endpoint as vpn.21x9.org and create the administrator account there. The Compose configuration sets INSECURE=true because Caddy terminates HTTPS and proxies to the local HTTP UI. Keep the UI behind Caddy and do not expose port 51821 publicly.

    Homepage configuration is managed through the docker.homepage dictionary in the host's group_data/<host>.py (for example, the ignored local copy group_data/@local.py). Each configuration area is optional and is rendered into its own YAML file:

    Host-data key Generated file Purpose
    settings settings.yaml Dashboard title, theme, layout and global settings
    services services.yaml Service cards and nested service groups
    bookmarks bookmarks.yaml Bookmark groups and links
    widgets widgets.yaml Global and service widget definitions
    docker docker.yaml Docker integration configuration
    kubernetes kubernetes.yaml Kubernetes integration configuration
    proxmox proxmox.yaml Proxmox integration configuration

    The templates serialize supplied Python dictionaries and lists as JSON, which is valid YAML. Use the structure and option names from the Homepage configuration documentation. Nested service groups and their layout can be expressed directly in host data:

    docker = {
    "homepage": {
        "image": "ghcr.io/gethomepage/homepage:latest",
        "port": 8020,
        "domain": "homepage.21x9.org",
        "settings": {
            "title": "Local Dashboard",
            "layout": {
                "Infrastructure": {
                    "style": "row",
                    "columns": 3,
                    "Server": {"style": "row", "columns": 2},
                    "Network": {"style": "row", "columns": 2},
                },
            },
        },
        "services": [
            {
                "Infrastructure": [
                    {
                        "Server": [
                            {"Portainer": {
                                "href": "https://portainer.21x9.org",
                                "description": "Docker management",
                            }},
                        ],
                    },
                ],
            },
        ],
    },
}

    Only keys present in docker.homepage are rendered. Omitted sections are not generated or removed; to clear a previously managed section, provide an empty list or dictionary as appropriate. The files are managed declaratively: manual edits to generated files are replaced on the next deployment.

    Migration note: The current templates use host bind mounts. If a host was deployed while an earlier Wallabag or Vaultwarden template used Docker-managed named volumes, Compose does not migrate that data automatically. Back up and copy the named-volume contents into the corresponding host directory before switching. Data already present in the host directories is retained.

    docker service configuration is independent of encrypted credentials. Put Miniflux credentials and the optional Vaultwarden admin-token hash in the encrypted secrets file; see Secrets management.

    Caddy and Sablier

    Software release pins are configurable in the local host data. Set caddy_versions.version, caddy_versions.sablier_plugin, and caddy_versions.dehydrated to select the Caddy image, Sablier Caddy plugin, and Dehydrated release used to build the custom Caddy image. The Sablier server image is selected with docker_sablier.version. All four values are required when their corresponding feature is enabled; no software-version fallbacks are used. Keep these pins in group_data/@local.py (or the appropriate host/group inventory data) rather than editing task or Dockerfile sources.

    caddy_config maps site addresses to Caddy directives consumed by tasks/caddy.py. Caddy is deployed inside the Docker feature gate when both docker and caddy_config are truthy. Dehydrated uses Hetzner DNS-01 credentials when at least one certificate is configured.

    Migration from dehydrated_domains: move ordinary certificate names into hostnames, configure their parent zones in dehydrated_zones, and move any manually requested wildcard certificate (including its SANs) into dehydrated_wildcards. The old dehydrated_domains setting is no longer consumed. Certificate names are derived from the list-based hostnames mapping only when they are fully qualified names inside dehydrated_zones. Configure this explicit zone allowlist; no DNS lookup or IP-address classification is performed. Private, reserved and public IP addresses are treated identically, which supports NAT and split-horizon DNS. Add internal-only names or IP addresses to dehydrated_blacklist to exclude them manually. An IP entry excludes every hostname mapped to that address; a hostname entry excludes only that name. Wildcard blacklist entries match exactly one label. A wildcard certificate is an explicit request covering its entire matching namespace; configuration fails if it overlaps a blacklisted hostname.

    Use dehydrated_wildcards for explicitly requested wildcard certificates, for example [["example.com", "*.example.com"]]; each inner list is one certificate and may include additional SANs. A flat list such as ["*.example.com"], an empty inner list, or another malformed entry is rejected; the error reports the offending certificate index, value and Python type to make host-data configuration mistakes easier to locate. Wildcards must fall within an allowlisted zone and suppress matching automatically derived names (one DNS label only). The dehydrated_auto_domains setting defaults to True; set it to False to disable automatic discovery entirely while retaining explicitly configured wildcard certificates. With no resulting certificate definitions, the Hetzner API token is not required and the generated Dehydrated domains file is empty. When certificates are configured, ensure secrets.dehydrated.hetzner_api_token is present and scope that token to the required Hetzner DNS zones where possible.

    docker_sablier is an optional mapping. Set enabled: True to deploy Sablier before service Compose projects are prepared. The supplied local configuration uses default_duration: "10m", blocking_timeout: "10m", and stop_dependencies: True. Caddy uses the dynamic strategy by default, with default_theme: "ghost", show_details: True, and refresh_frequency: "5s"; per-service overrides live under docker.<service>.sablier. strategy: "blocking" is available for clients that cannot use the dynamic loading page. blocking_timeout applies only to blocking mode.

    docker_power_save lists containers managed by the battery monitor. tasks/docker_power.py deploys the monitor and its systemd unit; the monitor is disabled while Sablier is enabled and re-enabled when Sablier is disabled. The two mechanisms are mutually exclusive.

    Syncthing

    Set syncthing to a dictionary to install Syncthing and enable its per-user systemd service (syncthing@<username>). The task uses the top-level username setting to select the service account and configures the GUI listen address through the Syncthing CLI. The GUI defaults to loopback-only (127.0.0.1:8384); change this only when remote access is deliberately secured, for example behind an authenticated reverse proxy or VPN.

    syncthing = {
    "gui_address": "127.0.0.1:8384",
}

    The package creates the device identity and initial configuration on first start. Add remote devices and shared folders through the Syncthing GUI or its CLI/API; this task does not replace the generated device identity or overwrite the complete config.xml.

    Firewall

    UFW supports the application/service keys chromecast-dlna, kdeconnect, localsend and ssh (TCP port 22), with Allow or Deny string values. It also accepts custom rules as dictionaries containing an action and a rule argument string. Custom rules are checked against ufw show added before they are applied, including normalization of UFW's optional in token, so repeated deployments do not add duplicate rules. Unsupported keys and invalid values are ignored.

    For example:

    ufw = {
    "ssh": "Allow",
    "kdeconnect": "Allow",
    "docker-host-https": {
        "action": "Allow",
        "rule": "in from 172.16.0.0/12 to 172.17.0.1 port 443 proto tcp",
    },
}

    The task sets default incoming policy to deny and outgoing policy to allow, applies configured rules, and enables UFW. Review the effective policy and ensure an independent recovery path before applying firewall changes remotely. Set firewall policy deliberately in the ignored local host configuration; the tracked example leaves UFW configuration empty.

    Secrets-dependent configuration

    The following features combine host data with encrypted secrets:

    • WireGuard requires wireguard_config plus matching secrets.wireguard entries.
    • Caddy's Dehydrated DNS-01 certificate workflow requires secrets.dehydrated.hetzner_api_token when Docker and caddy_config enable the Caddy task.
    • Git credentials are deployed only when secrets.git_credentials is present.
    • SSH key generation can use secrets.ssh passphrases.
    • Miniflux uses secrets.docker.miniflux for administrator and PostgreSQL credentials.
    • Paperless-ngx requires secrets.docker.paperless.postgres_password and secret_key.
    • Firefly III requires database credentials, app_key and a 32-character cron_token under secrets.docker.firefly-iii.
    • Snipe-IT requires database credentials and a persistent Laravel app_key under secrets.docker.snipe-it.
    • Linkwarden requires PostgreSQL, NextAuth and Meilisearch secrets under secrets.docker.linkwarden. The bookmark synchronizer reuses secrets.docker.homepage.environment.HOMEPAGE_VAR_LINKWARDEN_API_KEY, the same bearer token already supplied to Homepage’s Linkwarden widget; no separate token is required. The Linkwarden bookmark sync can be previewed manually from the repository root with python tasks/docker/linkwarden_bookmarks.py --dry-run; this does not download favicons or modify files. Omit --dry-run to apply the sync. The command decrypts secrets.json.gpg with GPG and reuses the Homepage API key.\n- Homepage can receive widget API keys through secrets.docker.homepage.environment; these values override matching host-data environment defaults.

    Adding a host

    1. Add a target entry to _all_hosts in inventory.py.
    2. Add its name to disabled_hosts until it is ready, if you want to prevent accidental selection through production.
    3. Create group_data/<host>.py with only the settings needed by that host.
    4. Verify SSH and privilege escalation.
    5. Run a dry deployment with a host limit and review every proposed operation.

    SSH client configuration

    Set ssh_config to a mapping of OpenSSH Host patterns to configuration lines. The tasks/ssh_config.py task renders these entries into the configured user's ~/.ssh/config.

    The generated file begins with a hardened Host * baseline that applies to all destinations:

    • HashKnownHosts yes hashes hostnames in known_hosts.
    • StrictHostKeyChecking accept-new accepts and records new host keys, but rejects changed keys.
    • UpdateHostKeys yes allows OpenSSH to learn additional host keys after a trusted connection.
    • PubkeyAuthentication yes and IdentitiesOnly yes prefer explicitly configured public-key identities.
    • ForwardAgent no, ForwardX11 no, PermitLocalCommand no and ClearAllForwardings yes disable common forwarding and local-command features.
    • ConnectTimeout 15, ServerAliveInterval 60 and ServerAliveCountMax 3 bound connection setup and detect unresponsive peers.

    The baseline is intentionally rendered before custom host entries. OpenSSH uses the first obtained value for most options, so later entries cannot override these baseline values. Other per-host settings remain available:

    ssh_config = {
    "github.com": """
  HostName github.com
  IdentityFile ~/.ssh/id_github
  User git
    """,
    "192.0.2.*": """
  User deploy
  Port 2222
    """,
}

    When connecting to a new host, verify its fingerprint through a trusted channel where practical. accept-new protects against changed keys, but the first connection still relies on trusting the key presented at that time.
